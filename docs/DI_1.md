當 TJ3-nRF 系統偵測到接點輸入 **DI1 或 DI2 變為 High（即進入警報狀態）** 時，根據開發式樣書的規範，系統會觸發一系列的判定、通報與紀錄動作：

### 1. 警報判定與延時過濾
*   **狀態確認**：系統會持續監測 DI 輸入狀態。當偵測到 ON（High）變化時，必須持續維持一段**「接點輸入判定時間」**（設定範圍為 1~999 秒）。
*   **雜訊排除**：如果在判定時間內接點恢復為原狀，系統將不會觸發通報，以防止誤報。
*   **環境限制**：若系統正處於**停電狀態**，由於無法進行監控，將不會執行接點變化通報。

### 2. 雲端通報 (MQTT Publish)
一旦確認警報成立，本機會透過 4G 模組將警報訊息發送至 AWS 雲端伺服器：
*   **發送電文**：使用識別碼 **`AD`**（接點通報）進行發送。
*   **Topic 格式**：`kyokuto/<MainID>/<PeriID>/AD`。
*   **Payload 內容**：封包內會標註具體的通道號碼（CH1 或 CH2）以及狀態值值 `1`（代表警報）。
*   **ACK 確認機制**：發送後會啟動計時器等待伺服器的 ACK 回應。若在規定時間內未收到 ACK，系統會執行**重傳（Retry）**；若超過重傳次數，則會嘗試重啟通訊模組或放棄該次通報。

### 3. 數據紀錄與儲存 (Data Logging)
警報狀態會被同步記錄在裝置內部的 Flash 記憶體中，供日後讀取：
*   **歷史紀錄**：DI1 與 DI2 的狀態會被寫入**「1 分鐘值即時量測紀錄」**（儲存 90 天）與**「30 分鐘值紀錄」**（儲存 1 年）的 CSV 檔案中。
*   **檔案內容**：在 CSV 的 `DI1_status` 與 `DI2_status` 欄位中，警報狀態會記錄為 **`1`**。
*   **停電保護**：在停電發生的瞬間，系統也會優先保存目前的接點 ON/OFF 狀態。

### 4. 藍牙狀態更新 (BLE Service)
若此時有手機 APP 透過藍牙連線，系統會更新相關資訊：
*   **警報 Flag**：當 APP 發送指令取得即時資訊（OP_CODE: `0xF6`）時，回傳封包中的 `AI_1_ALARM_FLAG` 位元組，其 **BIT_6 (DI_1)** 或 **BIT_7 (DI_2)** 會被置為 **1**。
*   **特徵值更新**：系統會更新 UUID 為 `...8c05` 的 **Alarm Status** 特徵值，這是一個 bitmask 格式的數據，方便 APP 即時呈現警報燈號。
